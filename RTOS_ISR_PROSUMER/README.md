# RTOS_ISR_PROSUMER

ATmega128과 FreeRTOS에서 **생산자·소비자의 공유 버퍼를 임계 구역으로 보호**하는 실습입니다. 생산자 5개와 소비자 5개가 8칸 원형 버퍼를 사용하고, LED와 LCD가 현재 데이터 개수를 표시합니다.

[전체 실습](../README.md) · [소스 코드](RTOS_ISR_PROSUMER/RTOS_ISR_PROSUMER/main.c) · [커널 설정](Source/include/FreeRTOSConfig.h)

## 실행하기

1. Microchip Studio에서 [솔루션 열기](RTOS_ISR_PROSUMER/RTOS_ISR_PROSUMER.atsln).
2. 대상 `ATmega128`, 클럭 `14.7456 MHz`를 확인하고 Debug로 빌드합니다.
3. 프로젝트의 `Debug` 폴더에 생성된 `.hex` 또는 `.elf`를 보드에 기록합니다.

Debug와 Release 모두 `-Os` 최적화를 사용합니다.

| 장치 | 연결 |
| --- | --- |
| LED 8개 | PB0~PB7, Active Low |
| LCD 데이터 | PA0~PA7 |
| LCD 제어 | PG0=RS, PG1=RW, PG2=E |

LED 극성이 반대인 보드는 `main.c`의 `LED_ACTIVE_LOW`를 0으로 설정합니다.

## 동작 확인

LCD 첫 줄에는 `Buffer Count:`, 둘째 줄에는 `Count = 3`처럼 현재 버퍼에 남아 있는 데이터 개수가 표시됩니다. 표시 범위는 **0~8**이며 LED도 데이터 개수만큼 켜집니다.

| LCD 숫자 | 의미 | LED |
| --- | --- | --- |
| 0 | 버퍼가 비어 있음 | 모두 꺼짐 |
| 3 | 소비되지 않은 데이터 3개가 남아 있음 | 3개 켜짐 |
| 8 | 버퍼가 가득 참 | 8개 켜짐 |

### 생산자 5개인데 최대 숫자는 왜 8인가요?

**5는 생산자 태스크 수이고, 8은 버퍼에 저장할 수 있는 데이터 개수입니다.** 생산자 하나가 반복해서 데이터를 넣으므로 데이터 개수는 생산자 수를 넘을 수 있습니다. 최대 저장 개수는 코드의 `BUFFER_SIZE`가 결정합니다.

생산에 성공하면 `count`가 1 증가하고, 소비에 성공하면 1 감소합니다. 생산과 소비가 함께 일어나므로 숫자는 오르내립니다. 화면에서 5까지만 관찰했더라도 코드의 최대값이 5라는 뜻은 아닙니다. 관찰 시간 안에 반드시 8에 도달하는 것도 아닙니다.

### 태스크 구성

| 태스크 | 개수 | 실행 간격 | 역할 |
| --- | --- | --- | --- |
| `vProducerTask` | 5 | 2~4초 대기 후 | 빈 공간에 데이터 저장 |
| `vConsumerTask` | 5 | 2~4초 대기 후 | 가장 오래된 데이터 꺼내기 |
| `vLCDTask` | 1 | 약 200 ms | 버퍼 개수 표시 |

11개 태스크는 모두 우선순위 1이며, 커널은 별도로 Idle 태스크를 생성합니다. 버퍼가 가득 차면 생산을, 비어 있으면 소비를 건너뛰고 다음 주기에 다시 시도합니다. 소비한 값은 읽은 뒤 사용하지 않습니다.

대기 시간은 고정 시드의 의사난수로 결정됩니다. LCD는 주기적으로 갱신하므로 LED와 순간적으로 다른 개수를 표시할 수 있습니다.

## 핵심 코드

`head`는 다음 저장 위치, `tail`은 다음 읽기 위치, `count`는 현재 저장된 개수입니다. 생산자는 아래 순서 전체를 하나의 임계 구역에서 처리합니다.

```c
taskENTER_CRITICAL();
if (count < BUFFER_SIZE) {
    /* 데이터 저장, head와 count 갱신, LED 변경 */
}
taskEXIT_CRITICAL();
```

소비자도 같은 방식으로 데이터 유무 검사, 읽기, `tail`·`count` 갱신을 보호합니다. `volatile`만으로는 여러 명령으로 이루어진 이 작업의 원자성을 보장할 수 없습니다.

이 AVR 포트는 SREG를 저장하고 인터럽트를 차단한 뒤 이전 상태를 복구합니다. 이름에 ISR이 들어가지만, 애플리케이션에 별도 `ISR(...)` 핸들러를 구현한 예제는 아닙니다.

LCD 태스크는 임계 구역에서 `count`만 복사하고 출력은 밖에서 수행합니다. 긴 LCD 출력이나 `vTaskDelay()`를 임계 구역 안에 넣지 않습니다.

## 설정과 오류 처리

| 항목 | 값 |
| --- | --- |
| 버퍼 크기 | 8바이트 |
| 애플리케이션 태스크별 스택 | 128바이트 |
| FreeRTOS 힙 | 2,800바이트 |
| 틱 주파수 설정 | 1,000 Hz |
| 힙 구현 | `heap_1.c` |

태스크 생성 또는 스케줄러 시작에 실패하면 `stop_on_error()`가 LED 전체를 켜고 정지합니다. 버퍼가 가득 찬 정상 상태에서도 LED가 모두 켜지므로 LED만으로 오류를 판단할 수는 없습니다.

## 예제 기준과 검증

강의 예제의 생산자·소비자 수, 버퍼 크기와 대기 주기를 유지했습니다. 태스크 스택은 80에서 128바이트로, 복사한 프로젝트의 힙은 1,500에서 2,800바이트로 조정했습니다. 난수 함수를 통합하고 태스크 이름을 `Prod`, `Cons`, `LCD`로 줄였으며 실패 처리는 `stop_on_error()`에 모았습니다.

참고 자료는 `10. RTOS_ISR_PROSUMER.pptx`의 4~15번 슬라이드입니다. 자료 원본과 별도 과제인 `RTOS_ISR_INTERLEAVED_LCD`는 포함하지 않습니다.

AVR-GCC 컴파일·링크는 경고 없이 통과했으며 `.elf`와 `.hex`를 생성했습니다. 당시 크기는 text 4,860바이트, data 62바이트, bss 2,918바이트입니다. 정적 SRAM 사용량은 힙을 포함해 2,980바이트입니다.

| 확인 항목 | 결과 |
| --- | --- |
| 프로그래머 연결 | AVRISP mkII를 통한 ATmega128 인식 확인, 전압 3.30 V |
| Flash 기록 | 확인 시점의 로컬 `RTOS_ISR_PROSUMER.hex`와 일치, Verify 통과 |
| LCD·LED 기본 동작 | 사용자가 보드에서 숫자 표시와 LED 개수 변화 확인 |
| 최대값 8 도달·장시간 안정성·스택 여유 | 아직 검증하지 않음 |

Flash 검증은 기록된 프로그램의 일치를 확인하는 절차입니다. LCD·LED의 기본 동작은 사용자 관찰로 확인했으며, 모든 실행 상황의 정확성을 검증한 것은 아닙니다.
